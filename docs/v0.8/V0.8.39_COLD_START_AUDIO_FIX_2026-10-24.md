# 万能输入法 v0.8.39 冷启动语音丢失修复

日期：2026-10-24  
版本：versionCode 49 / `0.8.39-cold-start-audio`

## 用户症状

点击语音后界面显示录音状态，但偶发没有文字。该现象在空闲一段时间后更容易出现。

## 根因

### 1. 冷模型启动期间没有录音

v0.8.36 为降低长期内存占用，引入了 60 秒空闲释放：独立 `:local_asr` 进程退出并释放 MNN 模型。旧流程为：

```
点击语音
→ InputSession 立即进入 LISTENING，UI 显示“正在收音”
→ LocalAsrService 加载模型
→ 模型准备完成后才启动 AudioRecord
```

因此，用户在模型冷启动期间说出的内容没有进入 PCM 管线。模型热态时启动很快，问题不明显；空闲释放后重新冷启动时就会偶发复现。

### 2. 正常停止可能被误判为录音故障

`SafeAudioRecorder.stop()` 会在另一线程中止阻塞的 `AudioRecord.read(READ_BLOCKING)`。Android API 允许 `read()` 返回负错误码。旧代码把所有负值都作为录音中断上报，即使此时是用户主动停止，可能先取消会话，再丢弃最终识别。

## 修复

1. 点击语音并成功提交 START 后立即启动 `AudioRecord`，不再等待模型加载完成。
2. 模型冷启动期间把 PCM 放入有界启动缓冲区；服务发出 ready 事件后按原顺序补送。
3. 用户已经说完而模型仍在加载时，先保存完成状态；模型 ready 后先冲刷 PCM，再发送 FINISH，不重复采样。
4. 仅在首个真实音频块到达后显示“正在收音”；此前显示“准备收音”。
5. 加入 4 秒麦克风启动看门狗和 2.5 秒无音频数据保护。
6. 区分“活动录音真实错误”和“主动 stop 导致的 read 结束”，后者不再触发错误取消。
7. 缓冲上限与 120 秒会话上限一致，超限明确失败，不静默丢掉开头语音。
8. PCM 发送由单一有序传输线程负责；增加 30 秒积压上限与 15 秒 FINISH 投递看门狗，传输堵塞时会重置独立识别进程并给出错误，不再无限停在“识别中”。
